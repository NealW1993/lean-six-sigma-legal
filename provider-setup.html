DATABASE SETUP

Choose your sync provider

Updated September 2, 2026

Personal and Shared Connections can use Supabase, Firebase, the bundled MySQL gateway, or another compatible HTTPS service.

Open server kits

01 What goes in the app

The app accepts an HTTPS endpoint, a mobile-safe public client key, and, only when needed, a temporary setup token. Database passwords, Firebase service accounts, JWT signing secrets, MySQL root credentials, and provider admin keys must stay on the server. Each device receives its own identity and rotating refresh token. Never paste these values into the app.

The publisher Supabase project used to verify optional Windows Pro linking is separate. It does not store projects, notes, tools, charts, shared-workspace content, or attachment bytes.

02 Supabase

  1. Create a project and enable Authentication > Sign-in Providers > Anonymous.
  2. In the app, open the visible Personal or Shared initial SQL + RLS panel and copy the complete script.
  3. Run the script once in Supabase SQL Editor. It creates tables, Auth membership, one-time invites, RLS policies, RPCs, and private Storage policies.
  4. Copy the Project URL and append the table path shown in the app.
  5. Copy an sb_publishable_ key or legacy anon key. Never use sb_secret_ or service_role.
  6. Save and run Test connection before turning on synchronization.

An optional sbp_ Personal Access Token can automate first-time setup. Revoke it after setup. RLS is the data boundary; the publishable key alone does not grant row access.

03 Firebase

  1. Create a Firebase project and enable Anonymous Authentication.
  2. Create Firestore and Cloud Storage in the same project.
  3. Download the Firebase server kit.
  4. Use Node.js 22 and Firebase CLI. Set unrelated SIX_SIGMA_CLIENT_KEY and SIX_SIGMA_SETUP_TOKEN secrets.
  5. Deploy the Function, Firestore rules, and Storage rules. Direct client access is denied; only the Admin Function handles data.
  6. In the app choose Firebase, paste the deployed sixSigmaApi URL and the Web API key from Project settings > General.

Set SIX_SIGMA_CLIENT_KEY to the Web API key entered in the app. Authorization still requires a verified Firebase ID token plus server-side vault/workspace membership. Attachments use object- and method-scoped signed URLs that expire after five minutes. An already issued URL remains usable until it expires, even if the device is revoked during that interval.

04 MySQL

The mobile or Windows app never connects to port 3306. Deploy the Deno/MySQL server kit and put its port 8080 behind an HTTPS reverse proxy.

  1. Copy .env.example to .env and generate a unique database password, JWT secret, public client key, setup token, and MySQL root password.
  2. Run docker compose up -d --build. A new database volume automatically runs the complete schema.sql.
  3. Keep MySQL on the private Docker network. Expose only the gateway through HTTPS.
  4. Configure request limits, rate limiting, redacted access logs, database backups, file backups, and restore tests.
  5. Choose MySQL server in the app and enter https://your-host/api, SIX_SIGMA_CLIENT_KEY, and the setup token for first owner setup.

MySQL does not provide PostgreSQL RLS. The gateway is therefore the mandatory authorization boundary: it binds writes to the verified device identity and checks active vault/workspace membership for every read, write, invite, permission, and file operation.

05 Custom HTTPS provider

Implement the Sync Protocol v1 OpenAPI contract. The provider may use PostgreSQL, SQL Server, MongoDB, DynamoDB, Firebase, MySQL, or another durable store, but it must preserve the protocol's authorization behavior.

  • Issue independent device identities and rotating refresh tokens; store refresh and invitation token hashes only.
  • Atomically consume invitations and enforce owner/member/inviter roles.
  • Ignore a conflicting client user_id and bind writes to the authenticated identity.
  • Return attachment URLs scoped to one object and HTTP method with an expiration no longer than 15 minutes.
  • Never return database credentials, signing keys, admin tokens, refresh hashes, or another device's token.

The in-app test verifies protocol negotiation and authentication. The service owner remains responsible for code review, dependency auditing, penetration testing, monitoring, backups, and incident response.

06 Verify before use

  • Use separate Personal and Shared scopes and test with two unrelated device identities.
  • Confirm a non-member receives HTTP 403 for every vault/workspace operation.
  • Confirm copied public keys cannot read data without a valid identity.
  • Confirm consumed invitations and rotated refresh tokens cannot be reused.
  • Confirm logs redact Authorization, client keys, setup tokens, invitation values, and URL query tokens.
  • Restore a backup in a non-production environment before trusting the service with important work.
